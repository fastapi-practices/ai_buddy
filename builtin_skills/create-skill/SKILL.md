# 创建技能

使用前先加载 `resource-tools` 能力获得所需工具；当前没有该能力时（如在 IM 通道或定时任务触发的对话中），告诉用户到网页端对话里操作，不要声称已完成

技能是按需加载的说明书：模型先只看到名称和说明，判断相关时才加载正文。`create_skill` 只生成 `SKILL.md`，不支持脚本和附件；需要这些时，让用户在客户端上传完整的技能目录或 zip

## 流程

1. 弄清技能解决什么问题、什么场景该触发、期望得到什么结果；用户已经说明的不要再问
2. 先在对话里给出草稿：`name`、`description` 和正文要点，请用户确认或提出修改
3. 按反馈修改草稿，直到用户认可后再创建；创建后的调整用 `update_skill`，不要重复创建
4. 调用 `create_skill`，用户会在创建前再确认一次参数
5. 创建后告诉用户：技能从下一轮对话起可用，可在技能列表中查看

## 修改已有技能

先 `list_resources`（kind 为 `skill`）取 ID，再调用 `update_skill`，只传需要改的字段：`description`、`body`、`version`。技能名称不能修改；`body` 要传完整的新正文，不是增量；改了内容建议同时升 `version`。内置技能不能修改，包内的其他文件不受影响

## 字段

| 字段 | 要求 |
| --- | --- |
| `name` | 最多 64 个小写字母、数字和单个连字符，不能以连字符开头或结尾，如 `weekly-report` |
| `description` | 最重要的字段，最多 1024 个字符，写清“做什么”和“什么时候用” |
| `body` | 正文，不含 frontmatter，frontmatter 由工具生成 |
| `version` | 默认 `0.1.0`，最多 32 个字符 |

## 写 description

模型靠它决定要不要加载技能，所以要同时包含能力和触发场景，并带上用户可能说的关键词。用第三人称陈述，不要写“我可以……”“你可以……”

- 好：整理会议讨论为纪要，输出决议、待办和未决问题；用户提到会议纪要、会后总结、整理讨论时使用
- 差：会议相关的技能

## 写正文

- 只写模型本来不知道的内容：团队约定、判断标准、固定格式、容易踩的坑，通用常识不要重复
- 建议结构：目标、适用场景、步骤、输出格式、边界与注意事项
- 步骤要可执行，输出格式给出具体样例
- 保持精简，能用几行说清就不要写成长文
- 不要引用不存在的脚本或文件，包内没有的资源模型读不到

## 注意

- 同一用户下名称不能重复；工具提示名称已存在时，换个名字重试
- `name` 不符合规则时工具会返回具体原因，按提示修正后再调用
- 工具返回创建失败时，不要告诉用户已创建
